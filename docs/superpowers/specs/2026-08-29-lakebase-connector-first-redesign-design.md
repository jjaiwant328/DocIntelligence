# DocIntelligence — Connector-First, Lakebase-Centric Redesign

**Date:** 2026-08-29
**Status:** Design approved (brainstorming), pending spec review
**Author:** Jaiwant Jonathan (with Isaac)
**Supersedes / relates to:** `docintel_sharepoint_mcp_lakebase_prompt.md` (the originating prompt), the current Lakebase migration (Project=UseCase, P1–P6).

---

## 1. Goal

Rebuild DocIntelligence into a **scalable, connector-first document-intelligence app** whose hot data layer is **Lakebase (managed Postgres)**, whose search runs **in Lakebase** (pgvector + full-text, no always-on Vector Search endpoint), and whose demo runs against an **external document source** (Google Drive first, SharePoint next) **without permanently copying originals into a Lakehouse Volume**.

The core flow the app is built around:

```
Connect a source
    → Inventory it (metadata only, no copy)
        → Build / Refresh a project-scoped index on demand
            → Hybrid search in Lakebase (semantic + keyword)
                → Open the authoritative source document
```

### Success criteria

- A Google Drive folder can be **inventoried without copying files** into a Volume.
- A user associates that folder with a DocIntelligence **project**.
- An explicit **Build/Refresh index** action creates/updates derived search data in Lakebase; **unchanged files are skipped**; deleted/moved files don't linger as false results.
- **Hybrid search** (semantic + keyword) returns source-aware results with a link to the authoritative source doc.
- **No always-on Vector Search endpoint** on the default path.
- The existing **skills + workflow engine still run a demo** — now sourced from the Lakebase-backed documents.
- The UI is **visually simpler** than the retired Control-Tower era.
- Existing Volume-based projects keep working during cutover (fallback), then legacy paths are removed once parity is confirmed.

### Non-goals (v1)

- Reproducing per-file Drive/SharePoint ACLs (demo uses **non-sensitive data**, with a visible banner).
- Rebuilding the ingestion notebooks; the deep analytical pipeline (ontology, gold tables) becomes an **optional** action, not the default flow.
- Conversational workflow assembly, portfolio dashboards, or the Knowledge Graph / Compliance Map / Action Center visual tabs (**retired**).

## 2. Decisions (locked in brainstorming)

| # | Decision |
|---|---|
| D1 | **Search backend = Lakebase.** pgvector for embeddings + Postgres `tsvector` for keyword, fused into one hybrid query. No always-on VS endpoint. |
| D2 | **Embeddings are generated by a Databricks embedding endpoint** (`databricks-gte-large-en`, 1024-dim) — Postgres stores & searches vectors, it does not generate them — and **stored in Lakebase**. |
| D3 | **Lean, visual redesign.** Retire Knowledge Graph, Compliance Map, Action Center from the shell (keep code, unwire). |
| D4 | **Keep a demoable Workflows + Skills path**, re-sourced from Lakebase-backed documents. |
| D5 | **Google Drive first** (already wired), **SharePoint next** as a second provider behind the same MCP-source abstraction. |
| D6 | **Migrate `domain_configs` / use-case config into Lakebase.** The lean path does not run the notebooks that read it from Lakehouse. |
| D7 | **Metadata-first, no persistent source copy.** Content is fetched temporarily for parse+embed, then discarded (retention configurable). "Open" re-fetches the authoritative source. |

### The one feasibility gate — RESOLVED ✅ (2026-08-29)

**Phase 0 spike passed.** Probed the live Lakebase (`ep-shy-block-e3xwzxuz…`): **PostgreSQL 17.11**, extension **`vector` 0.8.0** and `pg_trgm` 1.6 available; `CREATE EXTENSION vector` succeeded; cosine `<=>` ranking correct; **HNSW index created**; `tsvector` full-text confirmed. The primary design (Lakebase pgvector hybrid) is GO — no fallback needed.

**Fallback (now unused, kept for reference):** had pgvector been unavailable, we'd keep Lakebase for the full catalog + `tsvector` keyword search and generate semantic vectors into a minimal on-demand VS index. All vector access sits behind a `SearchBackend` interface (§5) so the swap would have been one file.

## 3. Architecture overview

```
                 SharePoint / Google Drive  (system of record)
                              │
          MCP source tools (list / metadata / fetch / changes)
                              │
                     ┌────────▼─────────┐
                     │  Indexer service │  crawl metadata (no copy)
                     │  (backend)       │  fetch+parse+chunk+embed on demand
                     └────────┬─────────┘
                              │  upsert
   ┌──────────────────────────▼───────────────────────────┐
   │                     LAKEBASE  (schema app)             │
   │  sources · external_documents · document_chunks        │
   │  index_jobs · projects · use_cases · workflow_runs      │
   │  document_chunks.embedding vector(1024)  (pgvector)     │
   │  document_chunks.tsv tsvector            (GIN)          │
   └──────────────────────────┬───────────────────────────┘
                              │  /api/search  (hybrid, project-scoped)
                     ┌────────▼─────────┐
                     │  FastAPI backend │  search · inventory · jobs
                     │  + skill_runtime │  workflows/skills over Lakebase docs
                     │  + workflow_eng  │
                     └────────┬─────────┘
                              │
                     ┌────────▼─────────┐
                     │  Next.js UI      │  Sources · Inventory · Search
                     │                  │  (Workflows/Skills = advanced)
                     └──────────────────┘
```

Two data planes collapse toward **one** (Lakebase). Lakehouse is retained only for the **optional** deep-analytical action (ontology/gold), not the default flow.

## 5. Backend components

### 5.1 `indexer/` (new)
- `crawl.py` — walk source metadata via MCP tools, upsert `external_documents` (no content). Bounded by folder/project scope.
- `diff.py` — compare source etag/hash vs `last_indexed_etag`; classify new/changed/moved/deleted/inaccessible; mark stale.
- `pipeline.py` — for changed+included docs: `fetch_document` (temp) → parse (text/pdf/docx/csv/xlsx via a light extractor; reuse `ai_parse` only where needed) → chunk (stable chunk_ids) → embed (batch) → upsert chunks/vectors → delete stale chunks → discard temp content unless retention on. Writes `index_jobs` progress.
- Runs as a **FastAPI background task** (or short Databricks job for large scopes) so API workers never block. Idempotent, resumable, retry-safe.

### 5.2 `search/` (new) — `SearchBackend` interface
- `lakebase_search.py` — hybrid query: pgvector cosine (`ORDER BY embedding <=> $q`) + `ts_rank(tsv, plainto_tsquery($kw))`, fused via Reciprocal Rank Fusion, filtered by domain/project/folder/type/status. Returns chunks + parent doc metadata + source link.
- `EmbeddingClient` — wraps the Databricks embedding endpoint (reuse skill_runtime model-call adapters).
- The interface (`search(query, filters) -> results`) isolates the vector store so the pgvector→VS fallback (§2) is a single implementation swap.

### 5.3 Routes (extend existing conventions in `docintel_routes.py` / `skill_routes.py`)
- `GET  /api/sources` · `POST /api/sources` (register, no secret) · `GET /api/sources/{id}/auth-url`
- `POST /api/sources/{id}/crawl` (bounded metadata sync) · `GET /api/inventory?project_id=` (source tree + status)
- `POST /api/index-jobs` (scope=file|folder|project|source) · `GET /api/index-jobs/{id}` (poll) · `GET /api/index-jobs?project_id=`
- `POST /api/search` (hybrid, project-scoped, source-aware results + citations)
- `POST /api/documents/{id}/refresh` · reconcile deletions/moves
- **Kept & re-sourced:** `/workflow-run`, `/skills`, `/skill-invoke` — document set now resolves from `external_documents`/`document_chunks` for the project (bridge below).
- Idempotent operations, correlation IDs, structured logs that exclude content and secrets.

### 5.4 Skills / workflow bridge — D4
The engine's document set (`$docs.*`) is populated from **Lakebase**: `external_documents` for the project (text via `document_chunks.snippet` or an on-demand `fetch_document`). Retrieval skills call the `SearchBackend` (Lakebase hybrid) instead of the VS endpoint. Net effect: the existing `compliance_audit` / reconcile demo runs unchanged over connector-sourced docs — this is the "same engine, new source" proof.

### 5.5 MCP source layer — D5
Extend `mcp_sources.py` + the sources MCP server:
- Add a **`sharepoint`** provider alongside `gdrive`.
- Add **metadata-crawl** tools to the no-copy path: `list_children`, `get_file_metadata`, `get_changes`, `check_access`, `get_source_url` (narrow, read-only surface). Keep `list_documents`/`fetch_document`.
- The legacy `/sources/import` (copy-to-Volume) stays available during cutover but is **not** the default path.

## 7. Security & authorization (demo-honest)

- App runs behind Databricks workspace OAuth; backend presents the **SP token** to the sources MCP server (existing cross-app pattern).
- **Credentials never in code/logs/prompts.** Google Drive: existing OAuth flow. SharePoint: **Keeper-managed** client secret for a **Microsoft Graph / Entra app registration** — stored as a `credential_ref` only. (Setup reference in §11.)
- **Explicit v1 limitation:** we do **not** enforce per-file Drive/SharePoint ACLs. The demo is restricted to **non-sensitive sample data**, and the UI shows a persistent banner stating this. A future `check_access` hook is stubbed in the MCP surface for later ACL trimming.

## 8. Cost controls

Scale-to-zero Lakebase; **no always-on VS endpoint**; manual Build/Refresh; project/folder-scoped indexing; incremental skip-by-etag; separate metadata crawl from content indexing; configurable embedding model/dim; configurable retention of snippet text + temp raw; cleanup of failed-job temp artifacts; per-run counts in `index_jobs`. A benchmark notebook records file counts/sizes, crawl/parse/embed/index durations, cold/warm search latency, live-fetch latency, unchanged-skipped count, and the compute/endpoint runtime — **numbers measured, not fabricated**, and labeled illustrative for a small demo corpus (idle endpoint cost is a published fixed number, looked up, not benchmarked).

## 11. SharePoint connector setup reference (for when we add it — P6)

To be executed by the repo owner via the approved credential path; **no secrets in this repo**.

1. **Entra (Azure AD) app registration** — register an app in the FE demo tenant; note **tenant ID**, **client ID**.
2. **Microsoft Graph permissions** — application permissions `Sites.Selected` (preferred, least privilege) or `Sites.Read.All`; `Files.Read.All`; grant admin consent. For user-delegated retrieval later: delegated `Files.Read`, `Sites.Read.All`.
3. **Client secret** — create in the app registration; store the value in **Keeper**; put only the **Keeper reference** into `sources.credential_ref`.
4. **Site scoping** — with `Sites.Selected`, grant the app read on the specific demo site collection only.
5. **App config env** (names to be confirmed against deployment manifests, not invented): `SHAREPOINT_TENANT_ID`, `SHAREPOINT_CLIENT_ID`, and a secret reference resolved at runtime — never the literal secret.
6. **Verify** with a Graph call: `GET /sites/{host}:/sites/{path}` then `GET /drives/{id}/root/children` — confirm metadata listing, then a single `GET /drive/items/{id}/content` for content fetch.
7. **Capabilities to verify (label verified/unresolved):** file-type & size limits, pagination/throttling (429 handling), delta/change tokens for incremental sync, and whether ACL retrieval is feasible for the demo.

Google Drive (P2, already wired) uses the existing `/oauth/google/start` flow — no new setup.

## 12. Open items / risks

- **pgvector availability** (P0) — the one hard gate; fallback defined (§2).
- **Graph throttling** on the zero-retention "re-fetch on open" path — mitigate with short-lived caching of the snippet.
- **Move/rename ID stability** — Graph item IDs are stable within a drive but can change across drives; the diff must treat an unresolved old ID as `deleted` and the new one as `discovered`.
- **domain_configs consumers** — confirm nothing on the *default* path still reads it from Lakehouse after migration; the optional notebook path gets a mirror.
- **`app/CLAUDE.md`** is stale (single-demo era) — updated in P7.
